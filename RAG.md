|      # | Box                         | Filled for your Predictive Maintenance RAG                                                                                                                                                                                                                                                                                                               |
| -----: | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|  **1** | **Problem & User**          | **Users:** maintenance supervisor, automation engineer, shift operator and Plant Head. Machines fail roughly every 2 days; the system should monitor live conditions, retrieve relevant historical incidents, and alert when maintenance may be required. A wrong recommendation could cause unnecessary maintenance or an expensive missed failure.     |
|  **2** | **Why RAG**                 | Historical maintenance notes, failure records and machine information are too large and heterogeneous for prompt stuffing. SQL alone works for structured telemetry but not unstructured maintenance knowledge; RAG lets us retrieve relevant historical cases and combine them with current machine conditions.                                         |
|  **3** | **Corpus Reality**          | Sources: PLC telemetry, CSV/JSON exports, dashboard alerts, maintenance logs, OEM documents and machine records across 60+ machines/two plants. Data comes in multiple formats, some is unstructured, and ~20% of machines have no telemetry. Data stays inside the air-gapped plant environment.                                                        |
|  **4** | **Parse & Chunk Plan**      | Chunk maintenance records **by maintenance/failure event**, not arbitrary token length. Machine documents can be chunked by section; telemetry should be converted into time-window/event summaries such as “6 hours before failure.” Validate by checking whether chunks retain machine ID, timestamp and failure context.                              |
|  **5** | **Index & Retrieval**       | Use **hybrid retrieval: embeddings + keyword/BM25 + metadata filters**. Metadata: `machine_id`, plant, vendor, machine type, timestamp, failure type, maintenance type. Use **local embeddings and a local vector store** because of the air-gapped network.                                                                                             |
|  **6** | **Permissions & Residency** | All operational data remains on-premise. Operators get machine-level read access; maintenance staff get maintenance/history access; Plant Head gets summary access. Audit every retrieval and recommendation.                                                                                                                                            |
|  **7** | **Freshness**               | Live telemetry is processed continuously by the monitoring layer. New maintenance records and failure events trigger re-indexing; telemetry summaries can be added hourly/daily or after significant events. Deleted/corrected records must also be removed from the index.                                                                              |
|  **8** | **Context Assembly**        | Prioritize: **current abnormal telemetry → same-machine historical failures → recent maintenance → similar-machine incidents → OEM/manual knowledge**. Drop old or low-similarity records first when the context limit is reached.                                                                                                                       |
|  **9** | **Architecture**            | **Live Telemetry → Anomaly/Rules Engine → RAG Retrieval → Reasoning Layer → Alert/Recommendation → Human Review.** LangGraph can orchestrate the workflow. Maintenance recommendations require human approval; no direct machine control.                                                                                                                |
| **10** | **Evaluation**              | Build a golden dataset from known historical breakdowns. Measure **retrieval Recall@K, groundedness, alert precision/recall, false-alert rate, failure-detection lead time and percentage of recommendations accepted by maintenance staff**.                                                                                                            |
| **11** | **Cost & Latency**          | Target alert generation within seconds/minutes depending on machine type. Use local embeddings and smaller/local models for routine requests; invoke larger reasoning models only for complex investigations. Compare system cost with the current ~$10M average stoppage impact.                                                                        |
| **12** | **Thin Slice**              | Start with **3–5 high-impact PLC-enabled machines**, their historical telemetry and maintenance logs, plus a live telemetry feed. Demonstrate one end-to-end alert showing current anomaly + similar historical failures + recommended maintenance investigation.                                                                                        |
| **13** | **Risks & Refusals**        | **1. Poor/missing telemetry:** flag insufficient evidence rather than predict. **2. No repeatable failure patterns:** fall back to condition monitoring. **3. Incorrect/hallucinated recommendations:** require retrieved evidence and human approval. Do not promise that every failure can be predicted or that AI will autonomously control machines. |
